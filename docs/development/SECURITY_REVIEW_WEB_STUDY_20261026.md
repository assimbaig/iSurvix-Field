## WS1 - Low: obfuscated loopback result links bypass the public-URL filter

Locations: `backend/core/web_references.py:63-74` and
`backend/static/core/js/qa_evidence_review.js`, `referenceURL()`.

The optional Brave adapter filters literal private/loopback IP addresses with
Python `ipaddress`, but accepts host spellings that are not parsed as IPs there
and are subsequently normalized by the browser. Its hostname filter also misses
`localhost.` with a trailing dot.

Reproduced backend acceptance and actual frontend normalization:

| Provider result URL | Actual frontend accepted URL |
| --- | --- |
| `http://127.1/private` | `http://127.0.0.1/private` |
| `http://2130706433/private` | `http://127.0.0.1/private` |
| `http://0x7f000001/private` | `http://127.0.0.1/private` |
| `http://%31%32%37.0.0.1/private` | `http://127.0.0.1/private` |
| `http://localhost./private` | `http://localhost./private` |

The ordinary test supplied a controlled Brave response and a synthetic fixture
key; the actual `search()` adapter returned `http://127.1/private` unchanged.
The real frontend controller's `referenceURL()` then returned the normalized
loopback URL, making it eligible for the result anchor. No real Brave key,
provider request, local-service request or link click was used. Receipt:
`url-normalization.json`, generated by `url-normalization.cjs`.

Impact is limited to an untrusted external result becoming a clickable local
destination for the authorized user. A provider/indexed-result influence and
user click are required. The default Wikipedia path constructs fixed Wikipedia
links and does not use the vulnerable result-URL path. The server's search
request still targets a fixed provider host: **this is not server-side SSRF or
an automatic local-network request**. No local response read, state change,
credential disclosure or approval bypass was demonstrated. Result links retain
`noopener noreferrer`; those controls do not validate their destination.

Recommendation, **pending approval**: canonicalize URLs with browser-compatible
host parsing before checking their destination, normalize trailing dots, and
reject canonical private/loopback/link-local hosts. Apply the same destination
policy to the final frontend URL. Add abbreviated, integer, hex, percent-encoded
and trailing-dot host cases to negative tests. Do not claim that syntactic
filtering alone prevents public DNS names from later resolving to private
addresses; no server fetch of result links should be introduced.

## Limits and deployment considerations

The completed study deliberately exposes internal saved observations to the
authorized Engineer/QA/Team Lead/Admin roles requested for this feature. It
remains read-only, paginates one photo/finding, and uses protected evidence URLs.
Client content follows the narrower accepted/released projection; Super Admin
engineering-access denial remains in the existing access service. No new bypass
of those tested boundaries was established.

The rate/duplicate probes establish **single-process** behavior only. The source
uses Django's configured cache, so separate process-local caches do not enforce
one shared global actor budget or in-flight lock. Before a multiworker deployment
relies on this quota, verify a shared atomic cache backend or durable limiter.
No multi-process production guarantee is claimed here. Cache/limiter deployment
changes require their own implementation and validation approval.

No live Wikipedia request was made by this reviewer; another agent's native
provider proof is not counted as independent AppSec evidence. No browser attack,
DNS-rebinding experiment, load campaign, fresh dependency advisory scan or hosted
production audit was performed. The new `requests` requirement is declared; this
review does not certify all versions allowed by its range. Phase counts remain
advisory progress and do not establish evidence quality or human approval.
